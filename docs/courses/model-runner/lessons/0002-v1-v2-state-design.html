01 / 共同任务

两个 runner 都要完成同一轮推理。

两者都消费 SchedulerOutput，维护请求和 KV block 信息，构造输入，调用模型，采样并回报。它们都位于 vllm/v1/worker/：MRV1/MRV2 是 V1 引擎内部 runner 的版本。

MRV1

gpu_model_runner.py

主要入口：_update_states()、_prepare_inputs()、execute_model()、sample_tokens()。

MRV2

gpu/model_runner.py

请求状态、输入准备、ModelState、Sampler、GraphManager 等拆到 gpu/ 的专门组件。

当前 MRV1 已有持久 batch、异步调度和独立采样阶段。区别要看数据组织和实现路径，不能只看功能名字。MRV1 execute_model · MRV1 sample_tokens

02 / 核心变化

持久状态行，不再等于本轮 batch 行。

MRV1：self.requests[req_id] 保存 CachedRequestState；self.input_batch 保存连续 batch 状态。请求暂时不被调度时，可以移出 batch、保留 requests；恢复时再加入。为了满足输入顺序，删除、填洞、重排时，要维护 token、block table、采样参数等关联状态。

“状态槽稳定”指这次活跃生命周期内，且不发生状态重建。当前 finish_requests 会移除 finished / preempted 请求；Streaming 输入更新也可能先移除再重建。它不是 KV block id，也不承诺恢复后仍是同一行。

04 / 对照表
变化发生在多个层面。
维度当前 MRV1MRV2
请求状态CachedRequestState + persistent InputBatch 协同RequestState 与 per-step InputBatch 分离
batch 顺序condense / 重排时维护关联状态根据顺序生成 idx_mapping，再 gather 输入
大状态更新维护 batch 的 CPU/设备缓冲和增量更新StagedWriteTensor 暂存差量，再由设备 kernel 写入
输入构造_prepare_inputs 中包含 CPU 数组构造与设备操作CPU 决定顺序/前缀和，设备 kernel 生成部分 token、position、seq_lens
异步安全synchronize_input_prep 保护复用 CPU 缓冲CPU 状态和在途快照分开；UVA buffer pool 等管理并发
采样与模型差异已有 Sampler 与模型相关处理gpu/sample/ + ModelState 生命周期更显式；仍要核对平台 patch
这是设计取舍：用映射与 gather 的设备工作，减少 batch 状态搬动与 CPU bookkeeping。新增 kernel、gather 和缓冲管理也有成本，不能仅由结构推导出固定提速比例。
