CHAPTER 05源码 · 例子 · 计算过程

启动时怎样建立缓存池

从 worker 内存预算到 num_blocks，再追踪设备分配、层绑定与 null block。

源码基线 / 2026.10.25vLLM 2f1041e8dd · Ascend e07bf18b76章节更新 / 2026.11.06

请求到来之前，设备上通常已经有一整片缓存存储。启动阶段要先回答两个问题：按模型需求，一份可分配的 block 有多大；按当前设备预算，一共能放多少份。只有规划完成，scheduler 的 block ID 与 worker 的 tensor 地址才有共同依据。

本章继续使用前三章的固定提交，以普通 decoder、单设备、无 offload、无 KV 传输和无投机解码为主线。所列容量是手算例子，不是 NPU 实测结果。模型权重、激活、通信与图执行占用仍需要留在缓存预算之外。

1. 启动链：谁决定什么？

阶段执行者与源码入口产生什么
声明需求模型缓存模块 → worker 收集 get_kv_cache_spec按层命名的 spec，包含 backend 定制
确定布局与预算EngineCore._initialize_kv_caches → executor / workers共同支持的 layout，各 worker 可用于 KV 的内存数
规划分配get_kv_cache_configs → 平台 builder各 worker 的 group、num_blocks、tensor placement
建立设备缓存initialize_from_config → runner.initialize_kv_cachebacking、逐层 view、Attention 绑定
建立管理对象scheduler 的 KVCacheManager → coordinator / BlockPool请求到 block 的记录、空闲队列、hash 索引

EngineCore 调 executor，executor 才把任务分发给 worker。这里不是由 scheduler 在收到每个请求时调用 torch.zeros 创建新的整份 K/V。scheduler 后续主要分配已建池中的 ID；worker 用这些 ID 访问此前建立的存储。

2. 可用 KV 预算不等于“当前空闲显存”

在这份 Ascend worker 源码中，自动估算路径通过 profile 得到非 KV 内存占用，再从 requested_memory 扣除。之后还有多 group、分层复用或 offload 等配置相关调整。理解普通路径时可以先写成：

普通路径的初始 KV 预算 = requested_memory − profile_result.non_kv_cache_memory

requested_memory 是当前引擎按配置确定的可用预算范围；non_kv_cache_memory 是该 profiling 路径统计的非 KV 占用。不能把操作系统报告的空闲量直接当作最终 KV 预算，也不能把模型权重只减一次就认为所有运行时峰值都已考虑。

3. 预算怎样变成 num_blocks？

取一个与上一章不同、但更接近容量量级的教学模型：本 rank 有 32 层，每层普通 GQA 的 Hkv=8、Dk=Dv=128、BF16，管理 block 覆盖 16 token。所有层同组、无额外 padding、无共享层。逐项计算：

每 token、每层 = 8 × (128 + 128) × 2 = 4096 bytes = 4 KiB
每页、每层    = 16 × 4096 = 65,536 bytes = 64 KiB
每个池 ID     = 32 × 65,536 = 2,097,152 bytes = 2 MiB
候选 ID 总数  = floor(6 GiB / 2 MiB) = 3072

这里 8 是本 rank 的 KV heads，128 是每个 K/V head 的元素数，2 是 BF16 每元素字节数，16 是每页 token 数，32 是这个 group 包含的层数。num_blocks 是池 ID 总数，不能再乘一遍层数得到“可分配块数”。层数已经计入每个 ID 的物理成本。

规划器还会检查模型最大长度能否装下，并处理覆盖配置与对齐。num_gpu_blocks_override 等选项会改变通常的取整结果。本例假设这些条件均不改变 3072 这个候选值。

多个 worker 时不能只拿 rank 0 的预算套全体。源码会按各 worker 的预算和本地布局分别求块数，再取其中最小值，重新生成较大者的 placement。例如一个 worker 能容纳 3072 个 ID，另一个只能容纳 3000 个，最终共同计数为 3000；如果各 rank 的每 ID 字节成本不同，总 backing 大小仍可能不同。

4. 真正分配的是 backing，再建立各层 view

默认 allocate_kv_cache() 检查所有 KVCacheTensor.size 描述同一份 backing，先创建字节 tensor，再逐个 placement 建 view。底层用 torch.int8 分配不表示缓存数值就是 INT8：它在这一步充当原始字节存储，后续由 spec 和 layout 解释为需要的 dtype 与 shape。

5. 管理器建立同一套 ID，并保留 null block

BlockPool 创建从 0 到 num_gpu_blocks−1 的元数据对象，把它们放入空闲队列，再取出 ID 0 作为 null_block。null block 用作占位，不像普通请求页那样维护引用计数，也不能被正常释放回空闲队列。

因此，前面的 3072 个物理 ID 中，通常有一个被 null block 保留。单池、无其他预留、无当前请求时，普通可分配 ID 为 3072−1=3071，对应 3071×16=49,136 个 token 槽位。池的物理 backing 仍是 6 GiB，不能因为 null block 不给请求使用就把它从设备分配量中减去。

小例子的 8 个 ID 同理：4096 bytes backing 已经存在，但普通请求最多使用其余 7 个 ID。在单 group 情况下，请求 A 的 10 个 token 需要 3 个 ID；两层有效 K/V 为 10×64×2=1280 bytes，请求容量为 3×256×2=1536 bytes，整个池仍是 4096 bytes。再加入一个请求，只改变 ID 的所有权与内容，不必让池整体增长。

6. 启动后怎样检查自己的理解？

沿源码或调试记录保留五份信息：最终逐层 spec、group 的层列表、各 worker 的 KV 预算、生成的 placement 和 num_blocks、逐层 tensor 的 shape/stride/storage。检查以下对应关系，比只记一个“KV 占了多少 GiB”更有用。

  • 每层是否归入预期 group，是否经过 backend 定制或平台覆盖？
  • 每个 placement 的页起点和末端是否落在 backing 范围内？
  • 多个 view 是否共享 storage？统计物理容量时有没有重复累加？
  • manager 的 ID 上限与 worker 分配的 block 数是否一致？
  • 日志中的总块数是否包含 null block，实际还剩多少空闲 ID？

这些检查解释初始化结果，不等于验证模型数值正确。要验证设备执行，还需要在对应 Ascend 环境运行并记录结果。下一章从这套已经初始化好的池出发，跟踪一个请求经过两轮 prefill 和一步 decode。
