先固定模型和问题

目标是从一个请求的 token 位置，找到一个具体层的 KV 存储位置。使用单卡、两层普通 GQA 模型：每层 4 个 Q heads、2 个 KV heads，K/V head dimension 都为 8，FP16，block size 为 4。无量化、context parallel、投机解码或 kernel block 拆分。这些微小参数用于演算，不代表某个硬件 backend 支持直接运行。

每层本轮生成的 key/value 可以分别是 [本轮 token 数, 2, 8]。这是当前计算的结果；长期 KV cache 保存历史结果，供后续轮次使用。每层的 K/V 来源不同，通常拥有各自的数据区域。

每层每 token：2 heads × (8 K + 8 V) × 2 bytes = 64 bytes
每层每 block：4 tokens × 64 bytes = 256 bytes

GQA 的 Q heads 分组描述多个 Q heads 如何共用 KV heads。因此这里用 2 个 KV heads 计算缓存容量，而不是 4 个 Q heads。

数据、规格、分配和映射

对象作用不应混淆的概念
KVCacheSpec描述一层的缓存需求、block size、dtype 和 page 大小不是已分配的数据 tensor
KVCacheGroupSpec描述共用 block table 的层集合同组不代表同一份 KV 内容
KVCacheTensor描述 backing 中的 layers、offset、layer stride、block stride它是布局描述对象，不是 torch.Tensor
torch.Tensor实际数据及其 shape、stride、dtype、storage 视图不同视图可以共享 storage，而不覆盖同一段字节
BlockPool管理编号、引用、哈希索引和空闲队列不执行设备上的 KV 大块内存分配
block table请求的逻辑 block 序号 → 物理 block ID表里存编号，不存 K/V 数值
slot mapping本轮各 token 对应的写入槽位槽位号不等于字节地址

读取一个变量之前，先确定它属于：需求描述、内存布局、资源账本、地址映射，还是实际数据。

从 position 算到 block ID 和 slot

请求 A 的 6 个 token 分成两个逻辑 block。分配器给出物理编号 2 和 7，因此 A.block_table=[2,7]。逻辑顺序连续，实际存储可以不连续。

logical_block = position // block_size
block_id      = block_table[logical_block]
offset        = position % block_size
slot          = block_id * block_size + offset

地址演算

固定 block_size=4、block_table=[2,7]。位置 6、7 是假设请求继续增长后的演算。

block table 用于描述请求历史块的映射；slot mapping 主要定位本轮新 KV 的写入。Attention 还要结合序列长度和 mask，决定读取哪些历史内容。

四种 group 分别划分什么

group划分对象设计职责
KV cache group缓存层共用请求到 block 的映射，统一管理分配和回收
AttentionGroup一个 cache group 内执行条件兼容的层组织 backend 与 metadata builders
GQA head group某个层内部的 Q heads多个 Q heads 读取较少的 KV heads
TP / DP / PP 通信组进程或设备 ranks组织并行切分、复制和通信

同一个 cache group 内仍可能因 backend、spec 或 Q head 数不同，产生多个 AttentionGroup。缓存管理上的兼容，并不意味着算子执行 metadata 完全相同。

Full Attention 与 Sliding Window 对历史的保留需求不同，因而可能分为不同 cache groups。具体分组还考虑 block size、规格兼容性和物理布局，不是单纯按类名分一次。

当前普通设备池路径中，各 group 管理器使用共同的 BlockPool。一个物理 block ID 同时由一个 group 占用；多个 group 不意味着每组都独占完整的一套编号容量。

共享映射、共享 storage、共享内容

两个层属于 group 0，A 在 group 0 的表为 [2,7]：

                    block 2              block 7
L0 cache view       L0 的 A 前4个 KV      L0 的 A 后2个 KV
L1 cache view       L1 的 A 前4个 KV      L1 的 A 后2个 KV
                    ↑ 同样的编号，解释为各层自己的 page ↑

管理器只需要维护一份映射，因为这些层对请求增长和块生命周期的要求一致。实际数据仍属于各层。只有模型显式设置 KV sharing 关系时，才需要进一步追“两个层读取同一份 KV 内容”的行为。

以 16 blocks、每层 page 256 B 为例：

布局layer_strideblock_strideL1 / block7 起点
层在外：L0 全部 blocks，再 L14096 B256 B4096 + 7×256 = 5888
block 在外：每块内放 L0、L1256 B512 B256 + 7×512 = 3840
page_start = allocation_base + descriptor.offset
           + layer_index_in_descriptor * layer_stride
           + block_id * block_stride

相同 shape 不保证相同物理布局。排查地址问题必须看 dtype、stride、storage offset、page padding，以及 backend 如何拆出 K/V 和 scale。上表是两种明确约定的布局演算，不是所有后端的通用地址式。

padding 补的不是同一种东西

位置原因需要检查
请求末尾 block 未填满按整块分配，6 tokens 占两个 4-token block有效长度；有空间不等于有有效 KV
page / block stride 对齐满足物理存储或算子对齐要求有效 page bytes 与物理 stride 是否不同
group packing 留白不同 group 使用共同池分配单位每个 group 实际成本与公共成本之间的差额
batch / 图执行形状补齐适配算子形状或图 replay 容量真实 token 数、padding slot 标记与写入 mask
block table 预留列固定容量缓冲区被重复使用请求当前有效条目数，不能读全部预留列

前两种影响容量与物理布局；batch padding 主要影响本轮执行形状。它们都不能通过“补的地方应该是零”来判断有效性。无效槽位与有效长度是接口契约的一部分。

manager block、backend kernel block 和 prefix hash block 也不必永远相同。本篇设为同一个粒度；遇到拆分时，需要继续追编号变换与 view 变换，不能只替换公式里的 block size。

从初始化到请求结束

初始化spec → group → 布局与容量 → tensor
→
调度分配 / 复用 block IDs，更新请求映射
→
执行生成 slot mapping，逐层写入与读取
→
回收减少引用，归还可复用 blocks

请求结束通常归还的是 block 使用权，长期预分配的 tensor 仍继续服务其他请求。开启 prefix cache 时，无引用 block 中的内容也可能继续保留到被驱逐；引用数归零不等于设备内存释放。

普通 Decode 采样得到 token 后，要到它作为输入参与下一次 forward，才产生自己的 KV。分配了 slot、知道 token ID、完成 KV 写入，是三个不同的事件。

合上正文，回答三个问题

1. position=6、block table=[2,7]、block size=4，slot 是多少？

核对答案

logical block=1，offset=2，物理 block=7，slot=30。两个同组层使用相同 slot 编号，在各自 cache 区域写入不同 KV。

2. 请求结束后，为什么设备内存用量可能几乎不变？

核对答案

block 的引用和空闲状态变化，预分配 backing 仍然存在。释放使用权不等于释放 storage。

3. group 里两个层，是不是每个 token 的 KV 只存一份？

核对答案

普通同组只共享管理映射。各层 KV 独立；显式模型 KV sharing 需要另查配置和绑定路径。
