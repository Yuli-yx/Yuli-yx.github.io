复用、回收与恢复

跟踪前缀身份、共享引用、淘汰与抢占，再解释滑窗和递归状态的恢复条件。

源码基线 / 2026.10.25vLLM 2f1041e8dd · Ascend e07bf18b76章节更新 / 2026.11.06

分配后，block 不只有“正在使用”和“已删除”两种状态。一个请求结束，页中的旧 KV 可能仍在，也可能仍可按前缀命中；一个页的引用计数降到 0，只表示它可以成为复用或淘汰候选，不等于设备内容已清零。本章从普通 Full Attention 的共享前缀开始，再讨论抢占、滑窗与递归状态的恢复边界。

基线仍为本书固定提交。数值例子采用单 rank、B=4、两层普通 GQA、每层页 256 bytes，开启本地 prefix caching；关闭 CP、投机解码、外部 KV 传输。凡讨论异步执行、滑窗或状态型缓存，会另行注明条件。

1. Prefix caching 比较的是什么？

普通 causal attention 中，同一位置的 K/V 依赖此前的输入上下文。因此，仅比较当前四个 token 是否相同不够。例如两条请求的某个 block 都是同样的四个 token，但更早的 prefix 不同，不能据此共享这个 block 的 K/V。

hash_block_tokens() 将父 block 的 hash、当前 block token IDs 和额外键一起放入 hash 输入。父 hash 把更早的 prefix 串入当前身份；额外键用于表达实现中需要区分的其他条件。模型服务里的 LoRA、多模态输入和缓存隔离等因素，应该追对应 extra keys 的产生位置，不能假设文本相同必然命中。

2. 两个请求共享前缀时，ref_cnt 怎样变化？

假设 A 已完成 10 个 token，表为 [5,2,7]。前八个 token 覆盖两个完整 block，ID 5、2 已登记可命中的前缀；ID 7 是 A 的尾块。随后 B 的前八个 token 与 A 相同，后两个不同。B 采用前缀命中后，只为自己的尾部申请 ID 3，表为 [5,2,3]。

时刻ID 5 的 ref_cntID 2 的 ref_cnt尾页情况
只有 A 使用117 属于 A
B 采用命中并持有前缀227 属于 A，3 属于 B
A 安全释放后117 可回收；3 仍属 B
B 也安全释放后00前缀页进入可淘汰队列，hash 可能保留

touch() 会增加引用计数；如果命中的页此前 ref_cnt 为 0，还会从空闲队列取下它。这里的引用计数是 manager 的 block 引用关系，不是 PyTorch tensor 的 Python 引用计数，也不是“有多少层使用这个 ID”。两层同组时，同一请求持有这组的 block，不因层数为 2 就自动把 ref_cnt 加成 2。

3. 释放引用、保留缓存和淘汰是三个动作

free_blocks() 先减引用。只有减到 0 的普通页才进入可复用队列；仍被 B 引用的页不能因为 A 结束就被另一个请求覆盖。带缓存 hash 的页与没有 hash 的页，插入队列的策略也不同：这个版本让无缓存页优先复用，让缓存页按相应的 FIFO 队列行为保留复用机会。

这些元数据动作通常不需要释放底层整个 tensor。旧数值可能一直留在设备字节中，直到新写入覆盖。某些执行路径需要清零新页来防止旧 NaN 或状态残留影响 kernel，runner 会按调度输出处理；所以“释放一定清零”和“从不清零”都不准确。正确性依赖有效长度、mask、写入范围和状态初始化共同保证。

源码还把可写页限定为非 null、独占且没有缓存 hash 的页。共享或已缓存状态不能随意原地修改。涉及可变状态恢复或尾部续写时，需要检查对应路径是否分配私有页、进行复制或限制命中位置，而不是只看到 ref_cnt=1 就判定可以改写。

4. 为什么全 prompt 命中，还可能要重算？

缓存保存的是 KV 等状态，不是本次生成所需的所有最终 logits。普通生成路径需要最后一个输入 token 的输出，因此 get_computed_blocks() 默认把最大命中长度限制为 request.num_tokens−1。在本例按整块命中且 B=4 的条件下：

新请求 prompt 长度允许的最大命中 token 数本例完整块命中长度还要执行的输入位置
10，前八个已有缓存988、9
8，八个全都有缓存744、5、6、7

第二行看起来只差一个 token，却因整块对齐而重算一整块。它不是所有配置下都必须重算四个 token：hash 粒度、命中对齐、模型类型和具体恢复路径可以改变结果。这里严格对应所引用函数的默认限制和本例完整块假设。

7. 递归状态恢复：要的是正确边界的状态

对 GDN/KDA 等状态型缓存，不能把第六章的“每个历史 token 都有一个独立槽位”直接搬过来。递归更新会把历史信息累积到当前状态；从第 k 个 token 后继续执行，需要与这个边界对应的 recurrent state，以及该实现所需的卷积等其他状态。只保留了末端状态，并不等于保留了任意中间位置的状态。

用一个纯教学记号表示：处理 p=0…7 后得到 S₈，处理到 p=9 后得到 S₁₀。另一请求要复用前八个 token，需要从 S₈ 及相应辅助状态开始；不能把 S₁₀ 当 S₈，因为后面两个 token 已经改变了状态。也不能继续原地写一个仍被其他请求当作 checkpoint 的 S₈。

上一章提到的状态集合若为 704 bytes，只表示一份集合的有效数值大小。若管理器还为运行状态、恢复 checkpoint 或投机状态保留额外页，应按实际保留份数与 padded page bytes 计费。MambaSpec.max_memory_usage_bytes() 在 align 分支和其他分支中采用不同的保留数量，具体哪一页扮演什么角色还要继续看 MambaManager 和 worker 的复制 / 更新路径。

8. 用三本账检查一次回收

账本需要回答的问题
请求逻辑账哪些 token 已被接受、哪些已处理，下一轮从哪个位置继续？
block 管理账各 group 持有哪些 ID，ref_cnt / hash / 空闲队列如何变化，有没有延迟释放？
设备数据账页里实际是哪一层、哪个边界的数据，是否仍有读写在途，view 是否共享 storage？

三本账对得上，才能判断“释放成功”“前缀可复用”或“请求可恢复”。仅观察某块内存仍有旧数值，不能证明它仍可用；仅观察 ref_cnt 为 0，也不能证明设备空间已经减少。本章完成了共同管理机制的主线，后面的真实模型案例会逐一补上各类 spec、状态和 backend 的具体条件。
