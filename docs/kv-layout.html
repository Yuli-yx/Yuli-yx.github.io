Cache spec、group 与物理布局

把模型缓存需求换算成页大小、分组和字节地址，区分每层页、池 ID 与共享 backing。

源码基线 / 2026.10.25vLLM 2f1041e8dd · Ascend e07bf18b76章节更新 / 2026.11.06

前两章分别讲“谁管理缓存”和“Attention 要保存什么”。这一章把两者接起来：模型声明的缓存需求，怎样变成管理器能分配的 block，又怎样对应设备 tensor 的一段字节？读完后，你应该能从一个 spec 算出页大小，从一个 block ID 找到某层的页起点，并解释为什么把所有 tensor 的大小相加会重复计数。

本章沿用 vLLM 2f1041e8dd 与 vLLM-Ascend e07bf18b76。先讨论单 rank、普通 causal GQA、BF16、无量化、无投机解码、无 KV 传输的例子；后面再引入混合 group。这里的数字用于手算，不代表某个模型或 backend 支持的实际启动参数。

1. Spec 描述需求，不持有缓存数据

模型层的 get_kv_cache_spec() 返回一个描述对象。它告诉规划器这一类缓存如何计算容量、覆盖多少 token、如何分配；并不会在这个调用里为每个请求创建 K/V tensor。第三章提到的 backend 定制可能改变声明，因此我们这里读的是规划时实际采用的 spec。

字段 / 属性含义普通 GQA 示例
block_size一个管理 block 覆盖的 token 范围；不要当作字节数4 token
num_kv_heads这一份缓存声明中的 KV head 数；并行时须核对本 rank 的值2
head_size / head_size_v每个 K / V head 的元素数，二者不必相等8 / 8
dtype普通数值元素的数据类型BF16，2 bytes / element
tokens_per_state一份存储状态覆盖多少 token1
page_size_bytes这一层一个管理页占用的字节数，可能含 padding256 bytes

这里把“层的一页”与“池中一个 block ID 的全部物理容量”分开叫。一个 group 可以有多层：管理器给这个 group 分配一个 ID，就要为该组的每层提供对应页。于是，一层的 page_size_bytes 通常不是整个池每个 ID 的字节成本。

2. 从元素数算到页字节数

先计算一个 token 在一层中的 K 和 V。K 有 2 heads × 8 elements = 16 elements；V 也有 16 个元素。两者合计 32 个 BF16 元素，乘每元素 2 bytes，得到 64 bytes。一个 block 覆盖 4 token，所以：

每 token、每层：Hkv × (Dk + Dv) × s
                 = 2 × (8 + 8) × 2 = 64 bytes
每页、每层：     B × Hkv × (Dk + Dv) × s
                 = 4 × 2 × 16 × 2 = 256 bytes

B 是每页 token 数，Hkv 是本 rank 的 KV head 数，Dk/Dv 是 K/V head 维度，s 是元素字节数。常见写法 2 × B × Hkv × D × s 隐含了 Dk = Dv = D，前面的 2 才代表 K 与 V。

源码进一步把页看成 head slot、stored state 和 cell content 三个维度：num_heads × num_states × state_content_size_bytes。普通例子中它们分别是 2、4、32 bytes，因此仍然是 256 bytes。若 backend 设置 num_head_slots 或 state_content_bytes，应读这些覆盖值，不能继续套普通 KV 公式。

假设一个教学压缩 spec 的 tokens_per_state = 4、block_size = 16，并满足实现的整除条件，那么每页有 16 / 4 = 4 份 stored state，而不是 16 份。具体状态的字节数仍由该 spec 决定。对 recurrent state，MambaSpec 按多份 shape 和 dtype 求和：例如 [2,8,8] FP32 为 512 bytes，[3,32] BF16 为 192 bytes，合计 704 bytes；这是一份状态集合的大小，不应再乘历史 token 数。

如果普通页的有效数值占 256 bytes，但 page_size_padded = 320，分配记账就采用 320 bytes，额外 64 bytes 是页 padding。它既不是新 token 的 K/V，也不是请求尾块的空位。这两个来源的浪费应分别记录。

3. Group 共享 block table，不等于层共享 K/V 数值

KVCacheGroupSpec 将一组模型层交给同一种管理方式。组内层共享请求的 block table。假设 G0 包含 L0、L1 两层，请求 A 在 G0 的表为 [5,2,7]：A 的第 0 个逻辑 block 在 L0 中用页 5，在 L1 中也用页 5。但 L0 和 L1 的页 5 通常处于不同的字节区间，保存各自层的 K/V。

不能只因为两个层的 dtype、head 维度相同，就认定它们一定同组。Full Attention 需要保留完整历史，滑窗层可能提前释放页，递归层还需要状态恢复位置。规划器必须让组内层能共同遵循分配、命中和回收规则。这个版本也支持 UniformTypeKVCacheSpecs，把需要相同 token 槽位数量、但逐层具体尺寸不同的 spec 放进一个 group；因此“一个 group 的所有层 shape 必须完全一样”也不准确。

默认规划路径先检查完全一致的 spec，再检查兼容的 uniform type，然后尝试其他分组与页大小统一方案。模型或平台还可以提供自己的 builder。读一个实际模型时，应先记下最终的 layer_names 和 kv_cache_spec，再讨论 group 数量，不从层数比例猜分组结果。

4. 用 offset 和 stride 找到真实字节

KVCacheTensor 在这里仍是分配描述。它给出 backing 大小、层列表、起始 offset、层 stride 和 block stride。某个描述中的第 l 层、物理 block b 的页起点是：

page_start_bytes = offset + l × layer_stride + b × block_stride

这里所有 offset/stride 的单位都是 bytes，l 是当前 layers 列表的下标，不一定等于模型的全局层号。这个公式只定位页起点；页内 K/V、head、token 的排列还要按 layout 与 backend 的 view 解释，不能直接把 slot 当作 byte offset。

5. 多个 group 为什么可以覆盖同一 backing？

再构造一个已完成分组的教学配置，使用 block-outer 布局。G0 的两层每层页 256 bytes，合计 512 bytes；G1 的一层页 384 bytes。假设相关对齐已经满足，规划器以较大的 512 bytes 作为每个池 ID 的跨度。8 个 ID 的 backing 仍为 4096 bytes。G1 使用某个 ID 时，384 bytes 放有效页，剩余 128 bytes 不属于该页的有效内容。

G0 和 G1 的 view 都可以描述全部 8 个 ID，并从同一 backing 的起点建立视图。但分配器不允许 G0 和 G1 同时占用同一个物理 ID。比如请求 A 的 G0 表为 [5,2,7]，G1 表为 [1,3,4]，两组共有六个不同 ID。G0 的 block 5 与 G1 的 block 1 不会冲突；如果两组同时把 ID 5 当自己的有效页，就会覆盖对方数据。

因而有三种不同数字：两个 group 的 view 可以共同引用 4096 bytes backing；请求占用六个 ID，对池的容量占用是 6 × 512 = 3072 bytes；这些 ID 中各层页的大小合计是 3 × 512 + 3 × 384 = 2688 bytes。两者相差的 384 bytes 来自 G1 的三份组间空隙，尚未扣除 token 尾块等有效数据差额。把每个描述里的 size=4096 相加，会把同一 backing 重复计算。

这个例子只说明已经确定的两组怎样摆放，不声称默认 builder 必然将某个模型分成这两组。特殊 host pool、HiSparse、平台自定义分配器和跨层共享还需要单独核查；这里描述的是引用源码中的默认设备 backing 路径。

6. 把四种“大小”放回各自位置

要问的问题应该查看的对象
一个管理 block 覆盖多少原始 token？spec 的 block_size，以及压缩 / 并行语义
某层的一页占多少字节？page_size_bytes、状态 shape、dtype、padding
一个池 ID 在设备上占多少容量？builder 的 pool bytes per block，不能只看某层页大小
kernel 如何读这一页？layout、tensor stride、kernel block size 和 backend 的 view

管理 block 与 kernel block 还可能不同。例如一个 16-token 管理 block 被 backend 虚拟拆成两个 8-token kernel block时，kernel 表和索引需要适配，不能直接把管理 ID 当成 kernel ID。具体拆分能力由 backend 决定。下一章将用确定下来的 page 与 pool stride，把内存预算转换成实际缓存池。
