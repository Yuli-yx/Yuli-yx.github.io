共建说明：要求、计划与接续方法

把写作约定、待办章节和维护方法留在仓库中，让后来的贡献者能够接着写。

这页记录本站的目标、写作要求、章节计划和接续方法。贡献者可以据此选题；换一台电脑后，也可以从仓库继续编写。需求有变化时，先更新这页和目录数据，再修改正文。最后更新：2026 年 10 月 27 日。

1. 我们要把什么讲清楚？

本站是一本围绕 vLLM 与 vLLM-Ascend 源码展开的推理系统读本。采用左侧目录、右侧正文的阅读形式。KV Cache 管理是其中一个专题；后续还会讲 P/D 分离、KV Pool 池化、PCP/DCP 和 Model Runner。

正文要让读者能沿源码回答：谁创建和持有对象，谁修改它，什么时候修改，它如何对应设备上的数据。KV Cache 专题尤其要区分逻辑 block、物理 block ID、KV cache tensor、block table 与 slot mapping，并跟踪 scheduler 和 worker 的分工。

2. 正文与计算怎么写？

  • 先说明前提，再给结论。写明源码版本、执行平台、模型配置、dtype、并行条件，以及当前讨论的是哪一层、哪个 rank 和哪个时刻。
  • 引入术语后给一个具体例子。用 shape、索引、表格或逐步执行过程，说明数据如何变化；不能只列类名和函数名。
  • 每个公式解释所有因子的含义、数值和单位。先算元素数，再算字节数，并用 tensor shape 交叉核对。
  • 分别计算有效数据量、请求分配容量和整个缓存池容量。注明尾块、共享、预留、量化 scale 和对齐是否计入，避免重复计算共享存储。
  • 教学参数、源码事实和运行观测分开表述。简化例子必须说明简化了什么，不把普通 GQA 的公式直接套到 MLA 或递归状态。
  • 按读者理解顺序组织段落，写清动作的主体和条件，保留必要的技术名称。参考 plain-chinese-writing，但不删掉理解机制所需的细节。

3. 源码与中文注释怎么放？

源码链接固定到 commit，并标明文件和原始行号。解释应落到实际分支、输入和返回值。涉及 backend 或 Ascend 覆盖时，要继续追踪平台实现，不能只看上游接口。

代码框中的中文补充统一以 # [讲解补充] 标识，用不同颜色显示，不占用上游行号。补充应解释当前代码的目的、条件或数据关系。它们不是上游原文，也不是可直接运行的代码改动。每个带注释的节选下方保留可展开的原始摘录，并链接到固定提交，便于逐行核对。

原始源码保存在 sources.json 和 model-sources.json；中文注释单独保存在 annotations.json，按原始行号插入。更新源码版本时，必须重新核对摘录、行号、注释和正文，不能仅替换 commit 字符串。

4. 当前进度与下一步

KV Cache 专题采用 16 章大纲，目录以 content/book/curriculum.json 为准。目前第 1–3 章已有正文：共同对象、Attention 结构、从配置追到实现。第 4–16 章仍待编写，不应把规划条目当作已经完成的说明。

下一批先补第 4–7 章：spec/group/layout、初始化、调度与执行、复用与回收。接着分别编写普通 GQA、Qwen3.5/3.6、Kimi K3、DeepSeek V4、GLM-5.3 和 GLM-5.3-Flash 案例。每个模型先核对具体 checkpoint 与配置，再确认 attention、缓存 spec 和平台实现；证据不足的部分明确留待核对。

模型案例统一记录：版本与运行条件 → 层与缓存组件 → shape/dtype/更新时机 → spec/group/物理视图 → 容量推导 → prefill/decode/恢复/结束 → 与其他模型的差异。最后做同一请求的横向对照，并衔接 PCP/DCP、P/D 和 KV Pool 专题。

其他专题目前保留入口与范围。已有文章和 MRV2 课程继续保留原 URL 与版本语境，不用新版本结论悄悄覆盖旧版说明。

5. 换电脑或开始贡献

公开内容和生成脚本都保存在 网站仓库，不依赖聊天记录或作者电脑上的服务。安装 Git 和 Node.js 后：

git clone https://github.com/Yuli-yx/Yuli-yx.github.io.git
cd Yuli-yx.github.io
npm run build
npm run check
npm run preview

没有推送权限的贡献者可以先 fork，再通过 pull request 提交。源码核查时，另行获取 vLLM 与 vLLM-Ascend 仓库，并 checkout 到页面标注的提交；不要求复制作者的本地路径或远程机器配置。

6. 提交前怎样核对？

  1. 检查源码链是否支持正文结论；将未确认的配置或运行行为写明。
  2. 复算公式，核对单位、shape、block 数、尾块与共享关系。
  3. 运行 npm run build 和 npm run check，检查链接和锚点。
  4. 在浏览器查看宽屏和窄屏目录、代码展开和交互例子，确认内容没有溢出或错位。
  5. 一起提交正文、证据、目录和生成文件；在提交或 PR 中说明改动范围、验证结果与尚未完成的部分。

GitHub Pages 从 main 分支的 docs/ 发布。推送后确认 Pages 构建对应本次提交，并打开线上页面检查。静态检查与教学演算不等于 NPU 正确性、模型兼容性或性能验证；声称实测时必须另附运行配置和结果。
