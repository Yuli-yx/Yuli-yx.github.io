PCP 与 DCP：每个 rank 看见哪些 KV？

用查询切分图、各 rank 的 block table 和本地页，解释 prefill 分工、DCP 交织写入与 decode 合并。

源码基线 / 2026.10.25vLLM 2f1041e8dd · Ascend e07bf18b76章节更新 / 2026.11.09

PCP（Prefill Context Parallel）把一次 prefill 的查询 token 分给多个 rank，主要用来缩短长 prompt 的首 token 延迟。DCP（Decode Context Parallel）把同一份 KV 的序列轴切开，多个 rank 各存一段。执行 decode 时，各 rank 用本地 KV 计算部分结果，再合并成完整的 Attention 输出。

读这两个特性时，先问三个问题：这个 query 由谁计算？对应的 KV 存在哪个 rank？当前 kernel 用的是哪组请求行和位置索引？这三个答案由不同的步骤决定。

1. 先看有哪些 rank

在这个版本里，每个 DP 副本、每个 PP stage 有 TP × PCP 个 worker。TP 划分模型计算，例如划分 Attention head。PCP 增加沿上下文协作的 worker。DCP 在这张 rank 网格上建立通信组，复用已经存在的 worker。

PCP 坐标 1全局 rank 2全局 rank 3

上图的 TP 组按行取，是 [0,1] 和 [2,3]。PCP 组按列取，是 [0,2] 和 [1,3]。如果设 DCP=2，源码按 PCP 坐标优先排列，所以 DCP 组也是 [0,2] 和 [1,3]。在第一组里，全局 rank 2 的 dcp_rank 为 1。后面算 token 归属时，用的是组内 rank。

如果某 backend 支持 DCP=TP×PCP=4，同一张网格会形成一个逻辑顺序为 [0,2,1,3] 的 DCP 组。可用的组合取决于模型和 backend。例如该 Ascend 基线对 GQA 的 PCP+DCP 组合要求 DCP=PCP。参见该版本的上下文并行支持表。

2. PCP 分 query，rank 仍能看到完整 KV

设只有一个请求 A，本轮 prefill 处理位置 p=0…7，此前没有已计算的前缀。取 PCP=2、DCP=1、TP=1，以有完整 KV 副本的普通 Attention 路径为例。每个物理页容纳 B=4 个 token。scheduler 为 A 分配物理页 [5,2]。

PCP 的 head–tail 切分把 8 个 query 分为 4 段，每段 2 个 token。rank 0 计算最早和最晚的片段，rank 1 计算中间两段。causal Attention 下，晚位置能看到更长的前缀，把早晚片段配在一起有助于均衡工作量。

在这个 PCP-only 路径里，各 rank 计算本地片段的投影，再通过 PCP 组交换 K/V 或写缓存所需的数据。同步后，两端各有一份对应自己 TP 分区的全序列 KV。rank 0 即使只计算了 p0、p1、p6、p7 的 query，也能让 p7 读到 p0…p7 所需的历史。block table 中的 5 指向本机缓存池的第 5 页，两端分别有自己的页。

一个全局请求可在某 rank 的本轮 batch 里拆成多条局部片段行。这个例子中，rank 0 的两条 A 片段行都用 idx_mapping 找回 A 的同一条请求状态，因此收集出的两条表行都从 [5,2] 开始。列的逻辑 block 编号不变，行的 query 范围和位置不同。Ascend 的 attention context 还保留 global batch 顺序的表，用于按全局请求组织历史和恢复顺序。这个 global 表同样由本 worker 的表收集而来，表项仍是本机物理页 ID。

3. DCP 的虚拟 block 怎样落到每个 rank

仍取 B=4，现在用两个 DCP rank 管理已写入的 10 个位置 p=0…9。固定一个参与 DCP 分片的普通 Attention cache group，令交织大小 I=2。全局连续的两个 token 为一组，轮流交给 rank 0 和 rank 1。每个 rank 的物理页仍有 4 个槽，一个虚拟 block 合计覆盖 B×D=4×2=8 个全局位置。

manager 用 ceil(T/(B×D)) 计算本例需要的逻辑 block 数，T=10 时得到 2。调度下发的两个 ID 都出现在 worker 表中，所以 rank 1 的尾页也已占用一个 ID，当前有效长度却只有 4。rank 0 的有效长度是 6。这就是 Attention metadata 还需要 dcp_local_seq_lens 的原因。仅看 [5,2] 无法判断每个 rank 有多少有效 KV。

5. Decode 怎样用各 rank 的历史得到同一个输出

以 Ascend 普通 GQA 的 DCP 路径为例，backend 准备每个 rank 需要的 query heads，读取该 rank 的 KV 与本地有效长度，计算局部 Attention 输出 Oᵣ 和局部 softmax 的 LSEᵣ。同一 query 会看到所有有效 KV 分片的贡献。组内的 query heads 如果已经相同，准备步骤可以复用当前 query。涉及不同 TP head 分区时，backend 需要相应的 head 交换。

Zᵣ   = Σ exp(score)                 # rank r 上可见 token 的分数总质量
LSEᵣ = log(Zᵣ)
m    = max(LSEᵣ)
wᵣ   = exp(LSEᵣ − m)
O    = Σ(wᵣ × Oᵣ) / Σ(wᵣ)

各 rank 的局部输出已经按本地 Zᵣ 归一化。合并时用 LSE 恢复相对权重。例如两个分片的 Z 分别为 3 和 1，输出权重就是 3/4 和 1/4。减去最大的 LSE 用于数值稳定。源码示例同时处理自然对数和以 2 为底的 LSE，权重分别用 exp 或 2^x 还原。

6. 读实际运行日志时对齐这几项

  1. 从并行组确认当前 worker 的 pcp_rank、dcp_rank 和 tp_rank，同时记下 DCP 组内 rank 顺序。
  2. 确认该 cache group 的 dcp_sharded、manager 页大小、kernel 页大小和生效的交织粒度（配置项 --cp-kv-cache-interleave-size）。这个版本的 SFA+DCP 按 block 大小交织，稀疏 indexer 还可能采用独立的复制布局。
  3. 同一请求同时记录全局位置、局部 query 行、block table 行、slot mapping 和每 rank 的有效 KV 长度。用图 2 的方法检查尾页与空 slot。
  4. 启用 P/D 或外部 KV 池时，把两端的 rank 组、交织粒度和 connector 约束一起核对。固定版本的 Ascend DCP 传输路径要求显式把 interleave 设为 block 大小。参见Ascend 上下文并行设计文档。
