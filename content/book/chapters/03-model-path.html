同一个商品名可能对应不同尺寸、量化方式或 checkpoint；同一个 architecture 字符串也可能被平台插件映射到不同实现。研究缓存之前，先找到真正被构造的类，再沿类的方法追到 spec。本章给出一条可复用的源码阅读路线。

以下示例基于固定提交，解释“怎样找到实现”。本章尚未加载各模型的权重，也没有将所有模型家族的参数视为相同。具体 checkpoint 的缓存总账将在后面的模型案例章中填写。

1. 先把模型和运行条件写完整

只写“Qwen3.6”不足以复现一次缓存规划。至少需要记录 checkpoint 标识与 revision、模型配置、vLLM/Ascend 提交、量化方式、并行配置以及会影响缓存的运行参数。

需要记录为什么影响判断
checkpoint、revision、配置文件决定 architecture、层数、层类型、head 数、维度和压缩等模型参数。
两仓 commit 与依赖版本同名类的字段和行为可能改变；引用源码时必须固定版本。
设备、TP/PP/PCP/DCP决定当前 rank 执行哪些层，保存哪些 heads、token 或状态。
权重量化与 cache dtype权重用低精度不自动意味着 KV 同样低精度，两者要分别记录。
block size、prefix caching、投机配置可能改变分配粒度、可复用边界、预留空间和状态副本数量。
实际 runner 与 Attention backend决定输入构造、布局适配和缓存读写接口。

记录时区分“用户给的值”与“框架解析后的值”。例如未显式指定的 cache dtype 可能由框架解析；不能把配置中的 auto 当成一种真实存储 dtype。

3. 在 decoder 层里找 Attention 的分支

顶层类名只告诉你模型入口，不能说明每层保存什么。继续查 decoder layer 的构造函数，重点看是否按层号或配置切换 Attention 类型。

Qwen3.5：按 layer_type 分支

源码明确区分 linear_attention 与 full_attention。前者构造 QwenGatedDeltaNetAttention，后者构造 Qwen3NextAttention。真正有多少层属于各类型，要从所选 checkpoint 的配置展开，不能从这个 if/elif 推断层比例。

{{source:qwen}}

Kimi K3：按 is_kda_layer(layer_idx) 分支

Ascend decoder 调用配置的方法判断某层是否使用 KDA；否则构造 MLA，并在该路径检查 no-RoPE 条件。这样可以确认这份实现存在两种缓存需求，但实际层数、维度和层分布仍由具体配置决定。

{{source:kimi}}

后面每个模型章都要列出“层号 → 模块类型 → cache 对象”的表。参数共享或多个缓存模块可能让两者不是简单的一对一关系，因此不能只统计 decoder layer 数。

4. 从模块追到最终参与规划的 spec

找到 Attention 模块后，继续读 get_kv_cache_spec()。这个方法可能定义在当前类，也可能继承自父类。若只在当前文件搜索不到，不应就此认定它没有缓存。

Qwen GDN 的 get_state_shape() 把 TP、K/V head 数、各自维度、卷积核大小和 speculative 参数传给状态 shape 计算器。这些参数能告诉我们接下来要核对哪些配置；真正的各项 shape 还需要读计算器的返回值。

{{source:state-shape}}

上游 V2 收集 spec 时，遍历注册到配置中的 AttentionLayerBase 模块，以 layer name 保存结果。代码会跳过共享目标层，忽略返回 None 的模块，并让 Attention backend 进一步定制 AttentionSpec。它还可能标记 draft 层或解析特殊缓存配置。

{{source:collect}}
区分原始声明与最终规划输入

某个模块的 get_kv_cache_spec 返回值，只是追踪过程中的一个节点。Backend 定制、平台适配和后续缓存规划可能继续改变字段。模型章节既要展示原始 spec，也要说明哪些步骤把它变成最终 config。

5. 在 Ascend 上再核对 runner 和适配路径

Ascend 可以通过模型注册、层替换、继承覆盖和 patch 改变上游执行路径。看到上游有某个实现，并不能证明这次 NPU 运行直接执行它。

当前源码的 runner 选择 patch 默认优先 V2，允许环境显式选择 V1，也会按配置中的特性限制回退。因此，V1 Engine、V1/V2 Model Runner、以及文件名中的 attention_v1 不能当作同一套版本编号。

{{source:runner}}

确认 runner 后，再找它调用的 spec 收集、缓存分配、block table 更新和 Attention metadata 构造方法。若某个方法继承上游，记录父类路径；若覆盖了它，比较实际改动。后续模型案例会把“上游机制”和“Ascend 差异”分别列出，避免同一段解释里来回切换却不说明对象。

7. 一次源码阅读的完成条件

读完一个模型的缓存实现后，应能用可核对的配置回答以下问题，而不只是报出一个 spec 类名：

  1. 哪个 checkpoint 在当前平台解析成哪个模型类？
  2. 每种 Attention 层及辅助组件分别保存什么？
  3. 哪些字段来自模型配置，哪些来自运行参数或 backend 定制？
  4. spec 怎样进入 group 和物理分配？
  5. 每个 tensor 的内容、shape、dtype、有效范围与生命周期是什么？

如果只完成静态阅读，就把结论限定为静态源码分析。需要运行才能确认的分支、布局或内存开销，留作明确的验证项。第 4 章将继续沿 spec 往下追踪，解释 group、page 与物理布局。
