分配后，block 不只有“正在使用”和“已删除”两种状态。一个请求结束，页中的旧 KV 可能仍在，也可能仍可按前缀命中；一个页的引用计数降到 0，只表示它可以成为复用或淘汰候选，不等于设备内容已清零。本章从普通 Full Attention 的共享前缀开始，再讨论抢占、滑窗与递归状态的恢复边界。

基线仍为本书固定提交。数值例子采用单 rank、B=4、两层普通 GQA、每层页 256 bytes，开启本地 prefix caching；关闭 CP、投机解码、外部 KV 传输。凡讨论异步执行、滑窗或状态型缓存，会另行注明条件。

1. Prefix caching 比较的是什么？

普通 causal attention 中，同一位置的 K/V 依赖此前的输入上下文。因此，仅比较当前四个 token 是否相同不够。例如两条请求的某个 block 都是同样的四个 token，但更早的 prefix 不同，不能据此共享这个 block 的 K/V。

hash_block_tokens() 将父 block 的 hash、当前 block token IDs 和额外键一起放入 hash 输入。父 hash 把更早的 prefix 串入当前身份；额外键用于表达实现中需要区分的其他条件。模型服务里的 LoRA、多模态输入和缓存隔离等因素，应该追对应 extra keys 的产生位置，不能假设文本相同必然命中。

{{source:m-prefix-hash}}

BlockPool 查找时还组合 cache group ID：同一串 token 对不同 group 的缓存内容不一样。请求 A 在 G0 的页不能因 token hash 相同，就被误认作 G1 所需的状态。命中返回的是已经存在的物理 block 引用，本地普通命中本身不需要复制整页 KV。

{{source:m-prefix-group}}

对于普通 Full Attention 的基础路径，按完整 block 复用最容易理解。但这个版本还有 partial block、细粒度 hash 和稀疏状态保留相关逻辑；“所有缓存永远只保存整块”不是本章要推广的结论。本例只使用完整前缀块，不分析那些特殊路径。

2. 两个请求共享前缀时，ref_cnt 怎样变化？

假设 A 已完成 10 个 token，表为 [5,2,7]。前八个 token 覆盖两个完整 block，ID 5、2 已登记可命中的前缀；ID 7 是 A 的尾块。随后 B 的前八个 token 与 A 相同，后两个不同。B 采用前缀命中后，只为自己的尾部申请 ID 3，表为 [5,2,3]。

时刻ID 5 的 ref_cntID 2 的 ref_cnt尾页情况
只有 A 使用117 属于 A
B 采用命中并持有前缀227 属于 A，3 属于 B
A 安全释放后117 可回收；3 仍属 B
B 也安全释放后00前缀页进入可淘汰队列，hash 可能保留

touch() 会增加引用计数；如果命中的页此前 ref_cnt 为 0，还会从空闲队列取下它。这里的引用计数是 manager 的 block 引用关系，不是 PyTorch tensor 的 Python 引用计数，也不是“有多少层使用这个 ID”。两层同组时，同一请求持有这组的 block，不因层数为 2 就自动把 ref_cnt 加成 2。

{{source:m-touch}}

两条请求的分配容量分别是 3×512=1536 bytes，逐请求相加得到 3072 bytes；但唯一被请求持有的 ID 只有 {5,2,7,3} 四个，实际占用池容量是 4×512=2048 bytes。共享的 1024 bytes 被两条请求各自账本计入过一次。这里 512 是该组两层的页总大小，池的整个 backing 仍保持 4096 bytes。

3. 释放引用、保留缓存和淘汰是三个动作

free_blocks() 先减引用。只有减到 0 的普通页才进入可复用队列；仍被 B 引用的页不能因为 A 结束就被另一个请求覆盖。带缓存 hash 的页与没有 hash 的页，插入队列的策略也不同：这个版本让无缓存页优先复用，让缓存页按相应的 FIFO 队列行为保留复用机会。

{{source:m-free}}

此时 ref_cnt=0、hash 尚在的页，既是“可命中的旧缓存”，也是“可分配时淘汰的候选”。两种身份并不矛盾。若新请求 C 在它被覆盖前命中，touch 会把它从空闲队列拿走并重新引用；若分配器先选中它交给别的内容，get_new_blocks() 会撤销旧缓存映射，再把引用计数变为 1。

{{source:m-reallocate}}

这些元数据动作通常不需要释放底层整个 tensor。旧数值可能一直留在设备字节中，直到新写入覆盖。某些执行路径需要清零新页来防止旧 NaN 或状态残留影响 kernel，runner 会按调度输出处理；所以“释放一定清零”和“从不清零”都不准确。正确性依赖有效长度、mask、写入范围和状态初始化共同保证。

源码还把可写页限定为非 null、独占且没有缓存 hash 的页。共享或已缓存状态不能随意原地修改。涉及可变状态恢复或尾部续写时，需要检查对应路径是否分配私有页、进行复制或限制命中位置，而不是只看到 ref_cnt=1 就判定可以改写。

4. 为什么全 prompt 命中，还可能要重算？

缓存保存的是 KV 等状态，不是本次生成所需的所有最终 logits。普通生成路径需要最后一个输入 token 的输出，因此 get_computed_blocks() 默认把最大命中长度限制为 request.num_tokens−1。在本例按整块命中且 B=4 的条件下：

新请求 prompt 长度允许的最大命中 token 数本例完整块命中长度还要执行的输入位置
10，前八个已有缓存988、9
8，八个全都有缓存744、5、6、7

第二行看起来只差一个 token，却因整块对齐而重算一整块。它不是所有配置下都必须重算四个 token：hash 粒度、命中对齐、模型类型和具体恢复路径可以改变结果。这里严格对应所引用函数的默认限制和本例完整块假设。

{{source:m-hit-limit}}

混合模型还要找到所有必要 group 能共同恢复的位置。不能只拿 Full Attention 命中的最长前缀作为整个模型的命中长度：若同一位置的 recurrent checkpoint 不存在，后续层就没有正确的起始状态。协调器负责各 manager 的命中协商；需要区分“某组有缓存”和“整个模型能从这里继续”。

5. 抢占后恢复：保留 token 序列，重新建立执行状态

当空闲 block 不足时，scheduler 可能把某个运行请求抢占，放回等待队列。引用源码中的 _preempt_request() 会释放或安排释放请求块，清理相关状态，把状态改为 PREEMPTED，并将 num_computed_tokens 重置为 0。

{{source:m-preempt}}

重置计算进度不等于把用户 prompt 和已经接受的输出 token 忘掉。恢复时仍有请求的 token 序列可以重算；如果旧页保留且 prefix caching 条件允许，也可能重新命中部分前缀。不要把该基础路径描述成“暂停时自动把全部 KV 搬到 CPU，再原样搬回”：offload 或外部 connector 的行为要另看其实现。

例如 A 已处理到位置 10，抢占前有三个逻辑 block。若恢复时还能命中前八个 token，就可从命中边界后重放剩余输入；若前缀已被淘汰，则要从更早处计算。重新分配的物理 ID 可以与旧表不同，但对相同 token 序列和模型而言，重算的目标仍是恢复正确的逻辑状态。

异步执行中还有一个时间边界：请求从 running 移走时，旧 kernel 可能仍在访问页。_free_request_blocks() 会检查是否可以安全归还，不可以时把 block 放进 deferred frees，等相应 fence 步骤完成才回池。否则新请求已经写入，旧 kernel 又回来覆盖同一个 ID，就会破坏数据。

{{source:m-deferred}}

6. 滑窗回收：丢掉表中的引用，保留逻辑位置

改用滑窗配置 W=4，仍令 B=4，无额外保留 token。若已经安全完成 p=0…6 共 7 个 token，下一个 query 是 p=7，它的窗口覆盖 p=4…7。按源码公式，可跳过 token 数为：

skipped = max(0, computed − W + 1 − extra_retained_tokens)
        = max(0, 7 − 4 + 1 − 0) = 4
可回收完整块数 = floor(skipped / B) = floor(4 / 4) = 1
{{source:m-window}}

若原表为 [5,2]，回收旧页 5 后，逻辑表相应位置用 null block 占位，概念上成为 [0,2]，不是压缩成 [2]。因为 p=7 的逻辑块下标仍为 floor(7/4)=1，它必须在下标 1 找到 ID 2；删除表项导致下标整体左移会把位置关系弄错。

{{source:m-skip-free}}

若只完成 6 个 token，skipped 为 3，floor(3/4)=0，第一块仍有窗口需要的数据，不能整页归还。可见有效窗口长度只有四个 token，并不意味着始终恰好占一页。chunk 大小、块边界、额外保留区和当前在途执行都可能增加驻留页数。

这份 manager 调用使用安全处理进度，并考虑 in-flight tokens，而不是直接按乐观调度进度回收。kernel 如果按 tile 读取窗口边界之外的数据，还需要正确的表项与 mask 处理。模型层执行滑窗计算，也不一定采用滑窗分配器；若配置退化为 Full Attention 分配，旧页的回收行为就不同。

7. 递归状态恢复：要的是正确边界的状态

对 GDN/KDA 等状态型缓存，不能把第六章的“每个历史 token 都有一个独立槽位”直接搬过来。递归更新会把历史信息累积到当前状态；从第 k 个 token 后继续执行，需要与这个边界对应的 recurrent state，以及该实现所需的卷积等其他状态。只保留了末端状态，并不等于保留了任意中间位置的状态。

用一个纯教学记号表示：处理 p=0…7 后得到 S₈，处理到 p=9 后得到 S₁₀。另一请求要复用前八个 token，需要从 S₈ 及相应辅助状态开始；不能把 S₁₀ 当 S₈，因为后面两个 token 已经改变了状态。也不能继续原地写一个仍被其他请求当作 checkpoint 的 S₈。

上一章提到的状态集合若为 704 bytes，只表示一份集合的有效数值大小。若管理器还为运行状态、恢复 checkpoint 或投机状态保留额外页，应按实际保留份数与 padded page bytes 计费。MambaSpec.max_memory_usage_bytes() 在 align 分支和其他分支中采用不同的保留数量，具体哪一页扮演什么角色还要继续看 MambaManager 和 worker 的复制 / 更新路径。

{{source:mamba}}{{source:checkpoint}}

这份源码还有两个明确限制。MambaManager 要求开启 prefix caching 时采用 mamba_cache_mode='align'。如果命中的末端状态是本轮其他请求刚登记的，管理器会返回超过整个池容量的需求数，让这个请求本轮不被调度。这是状态依赖限制，不是真的需要那么多显存。

{{source:m-mamba-mode}}{{source:m-mamba-step}}

需要写时复制时，runner 在新页清零之后、forward 之前消费 kv_cache_block_copies。从共享的 S₈ 续算到私有的 S₁₀，目标页必须先具有正确的起始状态，才能执行更新。这里引用的是通用复制入口；某个模型具体是否通过它复制、复制哪些数据，还要核对 manager 生成的计划。

{{source:m-state-copy}}

本章在共同机制层面强调恢复条件，不宣称每个 GDN/KDA 模型都支持相同 checkpoint 策略。后续模型章节会分别落实配置、checkpoint 对齐、写入时机、私有状态与共享状态的转换。判断一次命中是否可用，要同时满足身份一致、恢复边界一致、所有必需组件存在，以及数据已经可以安全读取。

8. 用三本账检查一次回收

账本需要回答的问题
请求逻辑账哪些 token 已被接受、哪些已处理，下一轮从哪个位置继续？
block 管理账各 group 持有哪些 ID，ref_cnt / hash / 空闲队列如何变化，有没有延迟释放？
设备数据账页里实际是哪一层、哪个边界的数据，是否仍有读写在途，view 是否共享 storage？

三本账对得上，才能判断“释放成功”“前缀可复用”或“请求可恢复”。仅观察某块内存仍有旧数值，不能证明它仍可用；仅观察 ref_cnt 为 0，也不能证明设备空间已经减少。本章完成了共同管理机制的主线，后面的真实模型案例会逐一补上各类 spec、状态和 backend 的具体条件。
