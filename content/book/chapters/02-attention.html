第一章把 token 位置映射到了缓存槽位。本章继续回答：这个槽位里究竟要保存什么？普通 Attention 保存历史 K/V；MLA 可以保存压缩表示；GDN、KDA 一类计算还需要维护递归状态。缓存内容变了，容量公式、更新方式和恢复条件也会跟着变。

先用小尺寸例子理解这些差异，再阅读实际模型。下面的数值都用于手算，不代表某个 checkpoint 的真实参数。源码依据仍是 2026 年 10 月 25 日固定的两份提交；本章没有运行设备实验。

1. 普通 Attention 为什么保留 K 和 V？

考虑一个 decoder 层的一个 Attention head。在位置 t，模型从当前隐藏向量产生 query（Q）、key（K）和 value（V）。当前 Q 与允许访问的每个 K 计算分数，把分数归一化成权重，再用这些权重对 V 求和。

score(t,j) = dot(q_t, k_j) / sqrt(Dk) + mask(t,j)
weight(t,:) = softmax(score(t,:))
output_t = Σ_j weight(t,j) × v_j

这里 t 是当前 query 的位置，j 是被读取的位置；Dk 是 Q/K 的 head 维度。对普通因果 Attention，位置 t 不能读取未来位置 j>t。mask 将这些位置排除。式子只描述一个 head；多个 head 的输出还需要后续组合和投影。

一步 decode 的具体输入

假设已经为位置 0、1、2 算好 KV，现在把位置 3 的 token 送进模型。当前层产生 q₃、k₃、v₃；计算输出时，q₃ 需要访问 k₀…k₃ 与 v₀…v₃。保留历史 KV，就不必重新执行旧 token 来获得它们。

本轮新产生：q₃、k₃、v₃
缓存中已有：k₀、k₁、k₂；v₀、v₁、v₂
本轮写入：  k₃、v₃
本轮读取：  k₀…k₃；v₀…v₃

下一轮位置 4 的 query 使用 q₄，不需要重新使用 q₃。

因此，普通自回归 Attention 的持久缓存通常保存 K/V，而不是全部历史 Q。这里说的是 Attention 的缓存需求；特定模型或投机执行路径可能另外保存 hidden states 等对象，不能由这条结论推断整个系统只保存 K/V。

Prefill 与 decode 沿用同一个因果关系

Prefill 可以一次处理多个 query。若一个 chunk 包含位置 4、5、6，位置 4 只能看到此前允许的历史与自己，不能看到位置 5、6；位置 6 则可以看到本 chunk 内更早的位置。实现可以批量计算，但每个 query 的可见范围仍由 mask 和长度确定。

这也解释了第一章的两类索引：slot mapping 指定本轮新 K/V 的写入位置；block table 结合长度等 metadata 帮助算子定位历史。两者都不代替 causal mask。

2. MHA、GQA、MQA 改变的是哪些 head？

Q heads 决定模型并行产生多少组 query；KV heads 决定要保存多少组 K/V。MHA 中两者数量相同；GQA 中多个 Q heads 共用一组 KV；MQA 可以看作只有一个 KV head 的情形。具体的 head 对应关系由实现确定。

做一组同口径比较：只看单 rank 的一层，不做 TP 切分；固定 Q head 数为 8，K/V head 维度均为 8，K/V 用 BF16 存储。这里的 BF16 每个数占 2 bytes。

结构Q headsKV heads每 token 的 K+V 数值大小
MHA882 × 8 × 8 × 2 = 256 bytes
GQA822 × 2 × 8 × 2 = 64 bytes
MQA812 × 1 × 8 × 2 = 32 bytes

每行算式依次是：K/V 两份 × KV head 数 × 每个 head 的维度 × 每个数的字节数。Q head 数没有直接出现在缓存容量公式中，因为这里没有统计 Q 的临时输入和计算工作区。

如果 K 与 V 的 head 维度不同，应改为 Hkv_local × (Dk + Dv) × bytes_per_element，前提仍是 K/V 使用相同 dtype、按普通数值布局存储。若使用不同 dtype，则 K、V 必须分别求字节数再相加。跨 TP rank 计算时，要使用本 rank 实际保存的 head 数，不能不看实现就把全局 head 数除以 TP。

普通 Attention 层会根据 Attention 类型和配置声明 spec。例如 encoder-only 层不需要自回归 KV，源码会返回 None。所以“模型中有 Attention 模块”并不必然意味着“这个模块占用一组持久 KV”。

{{source:ordinary}}

3. MLA：保存的可以是压缩表示

MLA 的关键在于低维表示。以包含位置编码分量的一种常见形式为例，模型把输入变换成压缩 latent，再由它产生 Attention 所需的部分 K/V；位置编码相关的 K 分量另行处理。在可使用压缩缓存的实现中，长期保存的是 latent 和需要的位置分量，而不是所有 heads 展开的完整 K/V。

这里只比较存储，不把简化示意当作模型完整公式。设一个 token 保存的 latent 长度 R=4，额外位置分量长度 Dr=2；二者都使用 BF16，无 scale、padding 或其他辅助项：

latent：4 个数 × 2 bytes = 8 bytes
位置分量：2 个数 × 2 bytes = 4 bytes
本例每 token 的缓存内容：8 + 4 = 12 bytes

这里不能再乘“2 份 K/V”，因为已经按实际保存的两个分量分别计数。它也不证明某个真实 MLA 模型只需 12 bytes/token：真实 R、位置分量、量化布局和辅助缓存必须从配置与实现确认。no-RoPE 的 MLA 路径也不能直接照搬上面的位置分量。

vLLM 的 MLAAttention.get_kv_cache_spec() 使用 MLAAttentionSpec 等类型，并将 num_kv_heads 设为 1。这里的 1 是缓存表示的字段，不能据此宣称模型只有一个 Q head。源码还对部分打包量化格式直接设置 state_content_bytes，因为此时实际字节数不能只用 head_size 推出。

{{source:mla}}

阅读 MLA 时要分别记录：数学计算使用的 Q/K/V 维度、长期保留的缓存分量、kernel 接收的 tensor view。这三个层面的 shape 不一定相同。Prefill 和 decode 也可能采用不同的计算形式，但仍使用同一套模型参数。

4. 稀疏、窗口和压缩，是三个不同问题

“本次只读少量位置”与“只存少量位置”之间没有必然等号。稀疏 Attention 可能通过 indexer 选择少量历史位置，却仍然保留大范围主 KV，以便后续 query 选择其他位置。要判断容量，必须同时检查保留策略与计算路径。

机制首先要问什么？不能直接推出什么？
滑动窗口当前 query 允许读取多远的历史？哪些旧位置可回收？逻辑窗口长度不一定等于最终分配字节数，还要按 block、对齐和保留策略计算。
稀疏选择从哪些候选位置里选出本轮要读的位置？不能把 top-k 直接当作缓存池最多存 k 个 token。
压缩表示一个存储条目代表多少原始 token，保存了哪些分量？不能把所有主缓存与辅助缓存都按同一压缩比例缩小。

例如，假设一个教学压缩器每完成 4 个原始 token 就产生一个存储条目。10 个 token 只完成两组，还有两个 token 的未完成尾部。若该算法需要保留尾部状态，完整账单必须把“两条压缩记录”和“尾部状态”分开。这是解释计数方法的例子，不是对 DSV4 或 GLM 实际尾部算法的断言。

DSV4 的实际源码说明了为什么需要逐项查证：indexer 的 spec 使用 tokens_per_state 表示压缩关系；compressor 的状态缓存则另有 spec、窗口与 padding。后面的 DSV4 案例会把这些对象逐个列出。

{{source:ds-index}}

5. GDN / KDA：维护状态，而不是逐项留下所有历史

GDN、KDA 一类递归计算可以用“旧状态 + 当前输入 → 新状态”来理解。下面只是接口关系，不是它们的数学更新公式：

S_t = update(S_(t-1), 当前输入及门控等参数)
output_t = read(S_t, 当前 query 等输入)

旧 token 对未来的影响进入状态 S。继续处理新 token 时，模型更新状态，而不是像普通 Full Attention 那样，为每个历史位置永久追加一份完整 K/V。具体实现还可能需要卷积历史、临时状态、投机副本和用于恢复的 checkpoint。

一个状态容量的手算例子

假设某个教学层需要以下两项，且只统计一份当前状态。它们不是 Qwen 或 Kimi 的真实 shape：

递归状态：shape [2,8,8]，FP32
  元素数 = 2 × 8 × 8 = 128
  字节数 = 128 × 4 = 512 bytes

卷积历史：shape [3,32]，BF16
  元素数 = 3 × 32 = 96
  字节数 = 96 × 2 = 192 bytes

一份状态内容 = 512 + 192 = 704 bytes

这里不能乘请求的 token 数 T，因为统计的是一份随输入更新的当前状态，而不是 T 份历史记录。如果执行策略需要保留多个状态副本或 checkpoint，还要按实际保留数量计算。每页的 padding 也应单独计入。

MambaSpec 的 shapes 与 dtypes 正是按这种方式描述状态：逐项计算元素数乘 dtype 字节数，再求和。名称叫 MambaSpec，不代表使用它的模型一定是 Mamba；阅读时要看实际层类型。该类还包含 speculative 和 prefill checkpoint 等字段，因此“状态本身不按历史长度线性增长”不意味着“运行中永远只分配一份状态”。

{{source:mamba}}

为什么恢复一个旧前缀需要额外考虑？

当前状态已经吸收了后续输入，通常不能直接把它当作较早位置的状态。如果要从某个前缀继续，需要对应位置的可恢复状态，或从可用边界重算。Qwen GDN 的代码中存在按条件补充 prefill checkpoint spec 的路径；这说明是否能恢复、恢复到哪里，要跟随具体实现和配置，而不能只凭模型属于“线性 Attention”判断。

{{source:checkpoint}}

6. 混合模型要逐层记账

Qwen3.5 的 decoder 根据层类型建立不同模块：linear_attention 使用 GDN，full_attention 使用普通 Attention 路径。两类层所需的缓存不能合并成同一种逐 token KV 公式。

{{source:qwen}}

先算一个教学混合模型：共 4 层，其中两层为 GQA，两层保存上述 704 bytes 的状态。GQA 每 token 每层为 64 bytes，block size 为 4；请求有 10 个 token，且全部计算完。无 prefix 共享、无额外状态副本，暂不计状态 padding：

两层 GQA 的有效 KV：2 × 10 × 64 = 1280 bytes
两层 GQA 的请求分配容量：2 × ceil(10/4) × 4 × 64 = 1536 bytes
两层状态内容：2 × 704 = 1408 bytes

有效内容合计：1280 + 1408 = 2688 bytes
按上述简化分配条件，占用容量：1536 + 1408 = 2944 bytes

这不是实际混合缓存池的最终分配结果。真实 planner 可能对齐 page、增加状态副本或组织共享 backing；要据实际 config 计算。这个例子只说明：先分别列出每类缓存，再按对应层数求和。MoE 的专家参数量也不能直接代入 KV 容量公式。

读完本章，应能先问对三个问题

这层保存哪些内容？每项内容按 token 追加，还是按窗口、压缩条目、递归状态管理？它的实际 shape、dtype 与保留数量从哪里得到？回答这三个问题以后，再开始算字节数。
