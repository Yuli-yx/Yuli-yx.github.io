现在设备缓存池已经建好。请求进来后，scheduler 决定本轮推进多少 token，并取得必要的物理 block ID；runner 把这些决定翻译成输入 batch、block table 和 slot mapping；Attention 才执行 K/V 写入与读取。本章按执行顺序逐项对照，特别区分“计划中的进度”和“设备已经完成的进度”。

教学配置：单 rank、一个 group、两层普通 causal GQA，B=4、Hkv=2、Dk=Dv=8、BF16，每层每页 256 bytes。池有 8 个 ID，0 为 null block。请求 A 有 10 个 prompt token；无 prefix hit、无投机解码、无 P/D、无 CP。本例按同步完成时点观察。指定 ID 只是便于演算，不代表真实空闲队列一定按此顺序分配。

1. Scheduler 先决定本轮推进多少 token

请求刚进入系统时，有 prompt token IDs 和请求配置，但还没有属于自己的设备 KV 页。scheduler 综合 token budget、请求状态、上下文长度、可用 block 等条件，决定本轮给 A 调度 6 个 token。此时 num_computed_tokens=0，本轮目标是位置 p=0…5。

对于本例的 Full Attention，如果已有的计算前缀长度是 C，本轮新增 n 个 token，不考虑 lookahead，那么需要能容纳 C+n 个 token 的页。需要的总页数为 ceil((C+n)/B)；实际新增页数还要扣除已持有的页和新命中的可复用页。本轮为 ceil(6/4)=2，假设取得物理 ID [5,2]。

allocate_slots() 会先让各类 manager 处理不再需要的块，再估算所有 group 的分配需求，检查剩余容量；不足时可返回 None。它还会考虑 in-flight 预留、水位线、外部命中、lookahead 等因素。因此实际代码并不是一个孤立的 ceil 公式。本例把这些条件关闭，是为了先看清普通路径。

{{source:m-allocate-slots}}

管理器返回的新 block 对象由 scheduler 转成 ID，放入 SchedulerOutput。新请求会带建立 worker 状态所需的信息；已在 worker 上的请求通常传增量 block IDs 和更新后的进度。这个消息传递的是执行计划与索引，不包含该请求的 K/V 数值。

{{source:output}}

2. Runner 更新请求表，再排列本轮 batch

worker 为请求建立常驻状态槽位 req_index。这个槽位是 worker 内部索引，不是请求字符串 ID，也不保证等于当前 batch 的第几行。新请求的表用 overwrite=True 从头写；已有请求的新增 ID 用 overwrite=False 追加。

{{source:m-new-table}}{{source:m-update-table}}

首轮收到 [5,2] 后，A 在 group 0 的有效 block table 行为：

逻辑 block 下标       0           1
覆盖 token          p=0…3       p=4…7
物理 block ID         5           2

这里只调度到 p=5，但第二页已能容纳 p=4…7。p=6、7 对应的槽位属于请求容量，尚不是本轮有效 KV。表的实际缓冲区可能预先开到 max_num_blocks；有效 ID 数、序列长度和 mask 决定哪些项可读，不能把整行的所有整数都当作有效历史。

runner 收集本轮请求的表行，生成 forward 使用的 block tables。若常驻槽位 A=3、B=8，而本轮 batch 顺序为 B、A，idx_mapping=[8,3] 就负责把 batch 行映射回常驻行。重排 batch 不会改变 A 的逻辑 block 顺序，更不会把 A 的页重新分配一遍。

{{source:m-prepare-attn}}

{{source:slot}}

一个 group 的 slot mapping 可供组内各层使用，但每层写的是自己的缓存 view。L0 写 p=0 的 K/V 到 L0 的页 5 偏移 0；L1 写到 L1 的页 5 偏移 0。这两份数值来自不同层，不会因为 slot 相同而变成同一份 K/V。

图执行可能把 token 数补到更大的长度。补出来的槽位会使用无效标记，并由 kernel 的有效范围或 mask 处理。本例表中只有真实 token，不展示 padding 项。CP、压缩存储或状态型缓存有自己的映射规则，不能拿这张表替代它们的 metadata。

4. Attention 写本轮 KV，读所需的历史

在某一层，输入 hidden states 经投影得到本轮 Q、K、V。Q 用于本轮 attention；K/V 要写进此前定位的缓存。Ascend 普通 Attention 的写入调用接收 slot_mapping，读取的 Paged Attention 路径则接收 block_table 和序列长度等信息。

{{source:write}}{{source:read}}

两类索引回答的问题不同：slot mapping 回答“这一批新 K/V 写到哪里”；block table 回答“当前请求的历史页在哪里”。对于 p=5，causal attention 只能读 p=0…5。它可以通过 ID 5 读第一段历史，通过 ID 2 读后半段；ID 2 中为 p=6、7 预留的槽位不应当作有效历史参与计算。

chunked prefill 中，本轮多个 query 的可见范围各不相同。p=0 不能看到 p=1…5，p=5 才能看到本轮之前的所有位置。最终行为要由 query 起止位置、历史长度和 causal mask 一起确定，不能只说“这一轮六个 token 都读到长度 6”。

这里引用的 Ascend 两个调用说明普通 backend 的接口契约。具体 prefill 可能走融合 Attention 算子，decode 也可能因 shape 和配置切换实现；不能推断所有模式都会执行同一个 Paged Attention 函数。追实际运行路径时，必须检查所在分支以及最终 backend。

6. 调度计数推进，不代表设备已写完

本章前面的账本选在各步完成之后。实际 scheduler 为了允许流水执行，会在 _update_after_schedule() 中把 num_computed_tokens 加上已调度数量，同时增加 num_in_flight_tokens。因此，若刚调度首轮就看到 num_computed_tokens=6，不能仅凭这一字段断言六份 KV 已经写入。

{{source:m-optimistic}}

例如调度后计数为 6、in-flight 为 6时，这一步的六个 token 仍可能在执行。模型结果返回后，update_from_output() 消费输出并处理采样、结束条件及相关计数；投机 token 被拒绝或旧输出失效时还需要修正进度。prefix hash 的登记也可能随调度提前发生，安全性要结合执行顺序、依赖和回收保护一起判断，不能拿“hash 已存在”当作任意消费者都能立即读取的证明。

当请求结束或被抢占，若仍有设备操作访问这些页，scheduler 可以先移出请求记录，把实际归还 block pool 的操作延迟到相应步骤完成。下一章会解释这一点：物理页重新分配前，必须确保旧执行不会再读写它。
