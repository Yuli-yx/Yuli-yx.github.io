谁在管理
KV Cache？

从一个 token 的位置出发，穿过逻辑 block、映射表与物理 slot，最终找到设备内存中真正的 K 和 V。

约 25–35 分钟9 个小节1 个交互实验
本文的源码基线vLLM · 2f1041e8dd ↗Ascend · e07bf18b76 ↗

理解 KV cache 管理，首先要把两个问题分开：“谁有权使用哪块空间？”和“这块空间里实际存着什么？”前者由 scheduler 侧的缓存管理器维护；后者由 worker 上的设备 tensor 承载。Block table 把请求的位置连接到这片空间，slot mapping 再为本轮新 token 指定写入位置。

本章先说明这几种对象如何配合。第 2 章解释不同 Attention 结构需要保留哪些数据，第 3 章说明如何从模型配置找到具体实现。

01 / CACHE OBJECTS

缓存数据、分配记录和位置索引

“一个 block”有时指请求的一段 token，有时指缓存池的一页空间。阅读源码时，如果不先分清这两层含义，很容易误以为每个请求都拥有一个独立的 KV tensor。

对象它描述什么它不是什么
逻辑 block请求的 token 分段请求内部连续的 B 个 token 位置，例如第 0 块覆盖 p=0…3。不是独立分配的 Python tensor。
物理 block / block ID缓存池的可分配单位缓存空间中的一个可寻址页；ID 由管理器分配，用于定位各层的对应页。ID 本身不是内存指针，也不是 K/V 数据。
KV cache tensor设备上的实际数据存储 K、V（或其他模型状态）的 tensor/view，包含许多物理 block。通常不是每来一个请求就新建一份。
Block table请求 → 物理页每个请求、每个 cache group 的有序 block ID 表。不是 K/V 向量的集合。
Slot mapping本轮 token → 写入槽位为本轮输入中的每个 token 指定物理 slot。不是请求的完整历史 token 表。

源码中的 KVCacheBlock 是什么？

KVCacheBlock 是 scheduler 侧的元数据对象，包含 block_id、ref_cnt、缓存 hash、空闲链表指针等字段。它管理一个物理 block 的身份与生命周期，并不持有该页 K/V 的 tensor。请求的第 j 个逻辑 block 对应哪个物理 block，要看请求的 block 列表。

把四个核心概念连成一句话

请求的逻辑 block 通过 block table 找到物理 block；slot mapping 指定本轮 token 在物理 block 内的写入槽位；KV cache tensor 才是该槽位里真正的数值存储。

02 / A WORKED EXAMPLE

一个请求，三块不连续的空间

设请求 A 的 prompt 有 10 个 token，用 t₀…t₉ 表示。这里下标表示序列位置，不是词表中的 token ID。为了手算方便，设每块容纳 B=4 个 token，缓存池有 N=8 个物理 block。

本章例子的边界

单 rank、一个 Full Attention cache group、无 prefix 共享、无 speculative decoding、无 context parallelism，且 manager block size 与 kernel block size 相同。B=4 是教学参数，不是后端配置建议；分配出的 ID 也是人为选择的例子，不代表分配器必然按该顺序返回。

t₀ · t₁ · t₂ · t₃映射到物理 block 5
t₄ · t₅ · t₆ · t₇映射到物理 block 2
t₈ · t₉ · — · —映射到物理 block 7

请求至少需要 ceil(10 / 4) = 3 个 block。假设管理器返回 [5, 2, 7]，那么这个列表的顺序对应请求中的逻辑先后；列表中的值对应物理页的编号。

block_table[A] = [5, 2, 7]
                  │  │  └── 位置 8…11 的物理页
                  │  └───── 位置 4…7  的物理页
                  └──────── 位置 0…3  的物理页

位置 8 和 9 已经需要第三页，位置 10 和 11 则仍是这页中的可用容量。分配了容量，不等于这些位置已经计算出了有效 KV。有效范围还要结合计算进度、序列长度和 mask 判断。

手算位置 p=6

① 找逻辑块j = floor(6 / 4) = 1

② 查物理块b = block_table[A][1] = 2

③ 找块内偏移o = 6 % 4 = 2

④ 得到 slots = b × B + o = 2 × 4 + 2 = 10

所以，位置 6 的 token 应把新 K/V 写到物理 block 2 的第 2 号槽位，也就是 slot 10。所有编号都从 0 开始。Slot 10 是索引，不是第 10 个字节，也不是一个单独的标量。

04 / WHERE THE VALUES LIVE
Slot 最终落到一个向量切片
下面选择一个便于理解的普通 K/V 视图。设本 rank 每层有 Hkv=2 个 KV heads，每个 head 的维度 D=8，dtype 为 BF16。在这个示意布局中：
K_layer.shape = [N, B, Hkv, D] = [8, 4, 2, 8]
V_layer.shape = [N, B, Hkv, D] = [8, 4, 2, 8]

# 位置 p=6 → 物理 block 2，offset 2
K_layer[2, 2, :, :]  ← 该 token 在这一层产生的 K
V_layer[2, 2, :, :]  ← 该 token 在这一层产生的 V

# 上面两项各自是 [2, 8] 的向量切片，不是单个数。


先把每个因子说清楚


这里计算的是当前 rank、当前一层的普通 K/V 数值容量。沿用本例参数：Hkv=2、D=8、B=4、N=8，dtype 为 BF16。K 与 V 的 head 维度在本例中相同；参数是为了手算而设定的，不是实际模型配置。


因子本例取值含义与单位


K/V 两份数据2一份 K，加一份 V。这个 2 不是层数，也不是请求数。


Hkv2 heads当前 rank 上每层的 KV head 数量；不是 Q head 数量。


D8 个数 / head一个 token 在每个 KV head 中的向量长度。


每个数的字节数2 bytesBF16 是 16 bit，16 ÷ 8 = 2 bytes。


B（block_size）4 tokens / block一个物理 block 能容纳多少个 token 的 KV。


N（num_blocks）8 blocks本例整个缓存池的物理 block 数，不是请求 A 的 block 数。




① 一个 token：先数元素，再乘字节数


一个 token 的 K 是 [Hkv,D]=[2,8] 的切片，包含 16 个 BF16 数值，因此占用 32 bytes。V 同样占用 32 bytes：


K：head 0 → 8 个 BF16 数值 → 16 bytes
   head 1 → 8 个 BF16 数值 → 16 bytes
                              合计 32 bytes

V：head 0 → 8 个 BF16 数值 → 16 bytes
   head 1 → 8 个 BF16 数值 → 16 bytes
                              合计 32 bytes

每个 token 的 K+V = 32 + 32 = 64 bytes
                 = 2 × 2 × 8 × 2 bytes
                   │   │   │   └─ 每个 BF16 数值占 2 bytes
                   │   │   └───── 每个 head 的维度 D=8
                   │   └───────── 本 rank 的 KV head 数 Hkv=2
                   └───────────── K、V 两份数据


例如位置 p=6 对应物理 block 2、offset 2：K_layer[2,2,:,:] 和 V_layer[2,2,:,:] 各是 [2,8] 的切片，各占 32 bytes。一个 slot 对应的是这个 token 的向量切片，不能把 slot 当作一个 BF16 标量。


② 一个 block：容纳 4 个 token 的 KV


一个 block 有 B=4 个 token 槽位，因此本层一页 K 加对应一页 V 的容量为：


每 block 的 K+V 容量
= 4 tokens/block × 64 bytes/token
= 256 bytes/block

其中 K 页占 128 bytes，V 页占 128 bytes。


③ 整层缓存池：预留了 8 个物理 block


本例这一层的缓存池容量为 8 blocks × 256 bytes/block = 2048 bytes = 2 KiB。也可以直接从完整 tensor 的 shape 交叉核对：


K_layer.shape = [N, B, Hkv, D] = [8, 4, 2, 8]
V_layer.shape = [N, B, Hkv, D] = [8, 4, 2, 8]

K 的元素数 = 8 × 4 × 2 × 8 = 512
K 的字节数 = 512 × 2 = 1024 bytes
V 的字节数 = 512 × 2 = 1024 bytes

K + V = 1024 + 1024 = 2048 bytes


三种口径：有效数据、请求容量、整个池容量


现在选择一个明确时点：请求 A 的 10 个 prompt token 已全部计算完，尚未计算位置 10 的输出 token 的 KV。沿用无 prefix 共享、无额外预留的前提，A 使用 [5,2,7] 三个 block。


统计口径计算方式本例结果


A 的有效 KV 数据量已计算的 10 个 token × 64 bytes/token640 bytes


分配给 A 的 block 容量ceil(10/4) × 256 bytes/block = 3 × 256768 bytes


这一层整个缓存池容量8 blocks × 256 bytes/block2048 bytes




三页可以容纳 12 个 token，但 A 只计算了 10 个。物理 block 7 中 offset 2、3 仍是未使用槽位，因此 A 的尾块空闲容量为 768 − 640 = 128 bytes，也就是 2 slots × 64 bytes/slot。


整个缓存池的本层 K+V 容量：2048 bytes
├─ A 所占三页的容量：768 bytes
│  ├─ A 的有效 KV：640 bytes（位置 0…9）
│  └─ A 的尾页剩余：128 bytes（可容纳位置 10、11）
└─ 不属于 A 的五页容量：1280 bytes
   它们可能空闲，也可能由其他请求或缓存占用；本例不作假设。


所以 640、768、2048 不能相加：它们描述嵌套的范围。640 bytes 位于 A 的 768 bytes 内，而 A 的 768 bytes 又属于整个池的 2048 bytes。尾页的 128 bytes 在本例中仍属于 A 所占用的页，并不是可独立分配给另一个请求的一整页。


下一步为位置 10 计算 KV 后，A 的有效数据增长到 11 × 64 = 704 bytes，但仍然只需要 3 个 block：请求分配容量保持 768 bytes，池容量保持 2048 bytes。这正好说明，有效数据增长不一定触发新 block 分配，分配新 block 也不等于扩建设备缓存池。


公式的适用范围
对本例普通、等维 K/V，每 token 每层的数值大小为 2 × Hkv_local × D × dtype_bytes。这里不计 block table 等元数据、量化 scale、padding、特殊 stride 或对齐开销，也不是整个进程的显存占用。其他层还需要自己的缓存；只有各层规格相同且没有缓存共享时，才可直接乘层数。MLA、K/V 不等维、量化或共享存储应按各自实际布局重新计算。



多层使用同一个 block ID，为什么不会互相覆盖？
对于本例中的普通多层 Full Attention group，请求在各层使用相同的 block ID 序列，但每层都有自己的缓存视图和对应的地址范围。K_layer0[2,2,:,:] 与 K_layer1[2,2,:,:] 表示不同层的内容。相同索引不意味着相同 tensor 或相同地址。
还要进一步区分“不同视图”和“不同分配”：当前 vLLM 的 allocate_kv_cache() 会创建统一的 backing buffer，然后按描述符构造各层 view；源码也明确说明 cache groups 可能覆盖同一 backing 区域。因此，不能把示意中的每层 K/V 画法理解成“每层都单独调用一次内存分配”。共享关系由 cache 规划、offset 和 stride 决定。

05 / TWO SIDES OF THE SYSTEM
Scheduler 管分配，Worker 管数据执行
CPU · 调度与元数据
Scheduler 这一侧
判断本轮哪些请求计算多少 token；向 KVCacheManager 申请或复用 block；维护请求进度、block 引用和释放条件。
请求 A → group 0 → [5,2,7]
设备 · Tensor 与算子
Worker / Model Runner 这一侧
维护请求执行状态和设备表；准备本轮输入与 metadata；运行模型，让 cache writer 写入 K/V，让 Attention 读取历史。
K / V tensor + 映射表 + 长度


这是一种职责分工，不是说 worker 只持有“数据”、不持有“元数据”。Worker 也有请求状态、block table、序列长度等执行必需的元数据；区别在于，常规调度路径中请求需要哪些缓存 block 的分配决策来自 scheduler 一侧。


  1. 启动时准备缓存池
    根据模型 cache spec 与内存预算形成 cache config，worker 分配 backing 并绑定层视图。
  2. 每轮做调度与 block 分配
    Scheduler 决定本轮计算多少 token，cache manager 判断已有容量是否足够，必要时补充物理 block。
  3. 下发执行描述
    通过 SchedulerOutput 发送新请求或已缓存请求的增量、block 信息和调度 token 数。常规这条消息不携带完整 K/V 数值。
  4. 构造设备输入与映射
    Runner 更新请求状态，应用 block table 更新，准备 positions、slot mappings 和 Attention metadata。
  5. 写 KV、做 Attention、返回结果
    模型每层产生本轮 K/V，并根据映射写入缓存。Attention 利用 cache、block table、长度和 mask 计算输出。Scheduler 据结果推进或结束请求。


Scheduler 的 schedule() 注释指出：其核心用 num_computed_tokens 追赶请求的待处理 token 数，统一覆盖 chunked prefill、decode 和 speculative decoding。这个统一调度描述，不妨碍后端为 prefill 和 decode 选择不同的算子路径。

请求槽位 ≠ 本轮 batch 行号 ≠ token 行号
V2 runner 中持久请求状态有自己的槽位。本轮 batch 顺序可能改变，因此需要 idx_mapping 将 batch 中的请求映射回持久状态行。gather_block_tables() 收集本轮 forward 需要的表行；slot kernel 也通过该映射定位正确的请求表。
当前上游 V2 的持久 block tables 是“每个 group 一张二维表”，dtype 为 int32；slot mappings buffer 是 [num_groups, max_num_batched_tokens] 的 int64 tensor。这里的 max 表示预留容量，不能把整个 buffer 都当成有效输入。本轮有效 token 数和 padding 处理同样重要。

为什么 slot mapping 常常每轮变化，而 block table 没变？
Block table 描述已分配的页。只要新 token 还在已有尾页里，就不用追加页；但每轮处理的 token 位置在变化，因此写入的 slot 也随之变化。


07 / FOLLOW THE LIFETIME
把分配、写入和释放放回时间轴
时刻A 的 block table本轮 slot mapping发生了什么
首次 prefill，p=0…5[5,2][20,21,22,23,8,9]分配两页，写入六个 token 的 KV。
继续 prefill，p=6…9[5,2,7][10,11,28,29]填充物理页 2 的尾部，并追加页 7。
decode 输入 p=10[5,2,7][30]已有尾页能容纳，无需新增 block。
decode 输入 p=11[5,2,7][31]写入尾页最后一个槽位。
继续计算 p=12[5,2,7,x][4x]需要新的逻辑 block，假设得到物理页 x。
请求结束移除请求关联无降低引用计数，符合条件的页回到可分配队列。


这个时间轴采用“按当前需求分配、没有额外预留”的简化情形。实际 speculative lookahead、外部 KV 加载或其他策略可能提前保留空间。
输出 token 已经采样，不代表它的 KV 已经算过
Prompt 的位置 0…9 执行完后，最后一个位置的输出可用于采样位置 10 的 token。这个新 token 通常在下一次 forward 中作为输入，才产生自己在各层的 KV；该次 forward 又用于预测后续 token。因此，不能把“已经拿到多少个输出 token”和“缓存已经计算到哪个位置”直接画等号。
释放 block，不等于释放整个设备 tensor
BlockPool.free_blocks() 的核心操作是减少 ref_cnt，在引用归零后按缓存状态放回空闲队列。它没有对每个请求逐一销毁设备上的 K/V tensor。释放的主要是对页的占用关系，缓存池 backing 仍可供后续请求使用。
如果启用 prefix caching，引用归零的页还可能保留可命中的 hash 与数据，直到被复用或淘汰。本章的无共享例子里，每页可以从引用 1 变为 0；多请求共享时，某一个请求结束不意味着该页立刻可复用。

09 / CHECK YOUR UNDERSTANDING
四个问题，检查是否真正连起来了
01在本例中，位置 p=9 应写入哪个 slot？
先自己算一遍，再选择答案。
02 · 为什么 block table [5,2,7] 不能告诉算子“只有 10 个有效 token”？
它只描述三页容量，最多覆盖 12 个位置。实际有效范围还需要 seq_lens、query 边界、mask 等信息，不能读取未计算位置。
03 · Layer 0 与 Layer 1 使用同一个 slot 10，数据会覆盖吗？
普通多层例子中不会：slot 是相对于各层缓存视图解释的索引；不同层映射到自己的有效地址范围。底层可以共享 backing，但必须结合层 offset/stride 理解。显式跨层共享或混合 group overlay 属于另行规划的情况。
04 · 请求结束后，为什么设备显存占用不一定立即下降？
回收的是该请求的 block 占用和引用；预分配 cache backing 仍在。后续请求复用这些页，不必反复向设备内存分配器申请和释放整块空间。
本章应掌握的一条链
token 的序列位置
→ 逻辑 block → block table → 物理 block + offset
→ slot → 各层 KV tensor 的向量切片
