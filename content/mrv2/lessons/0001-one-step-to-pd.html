01 / 先把名字对齐

MRV2 改的是哪一层？

MRV2 = Model Runner V2。Model Runner 负责把调度计划组织成设备上的一次模型执行。这里的 V2 指 runner 的版本；它仍在 vLLM 的 V1 引擎内。

名字这一课中的含义判断入口
vLLM V1 engine调度、执行、请求状态等组成的引擎体系vllm/v1/
MRV1 / MRV2V1 引擎内部两种 model runner 实现Worker 的 runner 选择分支
MooncakeConnectorV2一个 KV 传输 connector 的配置名称Ascend 的 connector 注册表

三个版本名称分别描述不同对象。启用了 MRV2，也需要另看 kv_transfer_config 才能知道用了哪个 connector。[1][2][6]

02 / 一轮执行的地图

先问“这一轮谁来算”，再问“怎么执行”。

假设这一轮只有两个请求：A 做 4 个 prompt token 的 Prefill，B 做 1 个 token 的 Decode。为便于理解，暂不加入投机解码和并行细节。调度给出 A: 4, B: 1，runner 把它们组织成一次执行所需的输入。[3]

Scheduler：这轮算谁、算多少

Scheduler 选择请求，决定每个请求本轮的 token 数和 KV block 分配，并把 connector 的本轮工作元数据放进 SchedulerOutput。它是执行计划；metadata 不是 KV 张量本身。

vllm/vllm/v1/engine/core.py:600 · vllm/vllm/v1/core/sched/scheduler.py:1464

Executor/Worker 把计划送到设备执行进程并选择 runner；MRV2 更新状态、构造输入并安排前向；Model/Attention 做计算；输出携带 token 与 KV 完成信息回到 Scheduler。

沿真实代码看，普通生成迭代可以压缩成下面几行。这里只表达顺序关系，省略异步、PP、pooling 等分支：

scheduler_output = scheduler.schedule(...)
model_output = executor.execute_model(scheduler_output, ...)
# 常规生成路径可能需要后续采样阶段
model_output = executor.sample_tokens(...)  # 按实际返回值/分支调用
scheduler.update_from_output(scheduler_output, model_output)

首选源码：EngineCore 的 step()。先读 600–616 行，看清闭环，再深入每个函数。

03 / vLLM 与 Ascend 接在哪里

主干复用，设备路径适配。

vLLM

GPUModelRunner

MRV2 入口是 vllm/v1/worker/gpu/model_runner.py。旧 runner 则在 vllm/v1/worker/gpu_model_runner.py。虽然类名都叫 GPUModelRunner，导入路径不同。

查看 GPU Worker 选择分支。[1]

vLLM-Ascend

NPUModelRunner(GPUModelRunner)

入口是 vllm_ascend/worker/v2/model_runner.py。它继承上游 MRV2；当前 execute_model() 调用 super().execute_model()，输入、缓存、图执行等有 NPU 适配。

还要连同 patch/worker/patch_v2/ 看最终绑定。[2][4]

阅读 MRV2 时，先认出四块：req_states 保存 runner 侧请求状态，block_tables 保存请求到 KV block 的映射，input_buffers 供本轮组织输入，model_state 封装模型相关的输入/Attention 状态逻辑。先知道职责即可，下课再拆数据怎么变化。[3]

第一次定位的动作：先从 Worker 确认实际 runner，再顺着方法跳到上游父类和 Ascend patch。只搜索 model_runner_v1.py，可能整条执行路径都读错。

04 / 把 P/D 放进同一张图

P 和 D 各有自己的调度与 runner。

在典型的 P/D 分离部署中，P 侧执行 Prefill，产生可供后续使用的 KV；D 侧获得所需 KV 后继续生成。MRV2 组织各自的模型执行，KV Connector 协调跨端缓存复用与传输。下图按数据方向画 P → D；当前 MooncakeConnectorV2 注册到 pull 实现，不能据此把它读成 P 主动 push 的调用链。[5][6]

P / Prefill 实例

Scheduler → Worker → MRV2

模型处理 prompt，写入本地 KV cache。

数据方向→所需 KV
D / Decode 实例

Scheduler → Worker → MRV2

获得可用 KV，继续模型执行与生成。

沿哪条线追传的是什么第一处入口
调度信息哪些请求/块需要外部 KV；本轮传输工作描述SchedulerOutput.kv_connector_metadata
缓存数据实际 KV 内存中的内容register_kv_caches() → connector worker 的加载/传输实现
完成回报哪些请求已经收完/发完，以及失败信息KVConnectorOutput → Scheduler

MRV2 给 connector 留了三个关键入口

pre_forward() 绑定本轮 metadata；同步 KV 加载在前向前启动，异步加载可延后到 post_forward() 提交。post_forward() 还收集 finished_recving / finished_sending 等回报。no_forward() 允许本轮不做模型计算时仍处理 connector 工作。[5]

读代码容易漏掉的一点：常规生成路径的 post_forward() 在 sample_tokens() 中调用。只在 execute_model() 末尾找“KV 是否传完”，会漏掉回报链。另一个分支是零 scheduled token：它走 no_forward()。[3][5]

这里给的是定位地图。不同 connector 的逐层等待、保存、传输提交和完成语义要分别读实现；方法名字相同，不保证内部做相同的事。
