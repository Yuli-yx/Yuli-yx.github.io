为什么不是只改一个 hash

底层 MemCache 可以保存字节，但它不知道这些字节属于哪个层、哪个 head、哪个状态边界。跨实例共享要同时回答：找哪个对象？对象是什么格式？读回本地哪里？什么时候才可读？只让两个 key 相等，不能保证 payload 兼容。

这里不是断言“原池化只支持 GQA”。原代码包含多类布局与后端路径；本次解决的是这几条路径之间统一的共享对象契约。也不是重新实现某个旧 PR 的 make_full_hash / make_partial_hash：当前完整块直接复用 request 的前缀 block hash，再由 SharedPoolLayout.key() 生成 PoolKey；PD 不完整块另有内容摘要。

layerwise：复用原发送线程实现层间重叠

最初版本在 forward 回调中 event.synchronize() 后同步拷贝，只有逐层粒度，没有计算—传输重叠。当前提交已经改为 StoreLayerTask 接入原 KVCacheStoreLayerSendingThread；没有新建另一套线程框架。

前台记录独立 ready event，提交完整块与 PD 状态 session；后台等待事件后执行原有 shared I/O 的 range copy。所有 session 的发布和租约清理由前台在 drain 之后完成，避免与后台修改 completed ranges 竞争。

use_layerwise=true 控制 P 写入的逐层时机；PD 的 D 仍整体读取完成后恢复计算。普通前缀池读取可以按层或整体执行。这三件事不能用一个“异步”词概括。

发布与租约：分配成功还不算命中

写：batch_is_readable → batch_alloc → 逐层/整体 batch_copy
    → drain → 校验所有 range 完成 → batch_write_finish → 释放租约

读：batch_add_lease → batch_get_key_info（地址与长度）
    → batch_copy → 完成读取 → 释放租约

查询使用 readable 状态，不以“已分配”代替“已写完”。batch_add_lease 返回状态码，不是对象地址。多个本地读取共享同一个 key 的租约引用；最后一个使用者结束后才释放。失败的未完成对象不能发布，也不贸然用删除操作补偿，以免误删其他 writer 共享的对象。
